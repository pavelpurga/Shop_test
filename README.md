## Описание
Проект демонстрирует каталог товаров с возможностью добавления в корзину. Данные получаются из публичного FakeStore API. Основные сценарии:
- Просмотр каталога (карточки товаров)
- Поиск, фильтрация по категориям, сортировка
- Пагинация (12 товаров на страницу)
- Корзина: добавление/удаление и изменение количества, сохранение в `localStorage`
- Skeleton loaders, toast‑уведомления, lazy‑загрузка страниц (code‑splitting)
- Тёмная тема с сохранением выбора
- Кэширование запросов (React Query)

## Технологии / зависимости (и почему их выбрали)
Коротко... какие технологии используются и зачем они подходят для этой задачи.

- React — требование по ТЗ, а также до этого был опыт коммерческой разработки.
- TypeScript — даёт статическую типизацию, помогает получить ошибку быстрее, чем это сделает team lead.
- Vite — простой конфиг и хорошая производительность на больших проектах, перед выполнением данного ТЗ практиковался в pet-проекте его использовать.
- React Router — стандартная маршрутизация.
- Redux Toolkit — меньше шаблонного кода по сравнению с "raw" Redux, можно было использовать Zustand, однако в перспективу развития любого проекта везде опытные люди рекомендуют использование  RTK.
- @tanstack/react-query — для работы с удалёнными данными: кэширование, управление состояниями загрузки/ошибки, упрощает повторные запросы и инвалидацию.
- CSS Modules — изоляция стилей на уровне компонентов без глобальных конфликтов; простой и предсказуемый подход.
- React Testing Library + Vitest — Vitest даёт быстрые тесты в среде Vite, а первое - стандартная библиотека для тестирования компонентов.

Почему я выбрал именно это:

- Я предпочёл связку Vite + TypeScript, потому что для небольшого, но реального SPA важна высокая скорость разработки и строгая типизация: Vite даёт мгновенный HMR и быструю сборку, а TypeScript снижает количество простых ошибок.
- Для управления состоянием корзины я использовал Redux Toolkit: мне нужен предсказуемый глобальный стор с понятной архитектурой и хорошей поддержкой TypeScript. Я рассматривал вариант с Zustand, но выбрал RTK, по вышеописанной причине.
- Для запросов к API использовал React Query — потому что она вводит кэширование, рефетчинг и стратегии stale/timestamps «из коробки», и мне не пришлось вручную организовывать сложную логику кэширования и состояний загрузки.
- CSS Modules выбрал ради простоты и предсказуемости: локальные классы, минимальная магия и отсутствие runtime‑зависимостей. Альтернативы (Tailwind, styled-components) хороши, но для этого задания я хотел ограничить набор новых парадигм и оставить стили очевидными.

Почему не использовал некоторые альтернативы:
- MobX — отличный инструмент, но он вносит иную модель реактивности и требует дисциплины; для команды/портабельности я предпочёл RTK.
- Чистый Context для cart — возможен, но может привести к лишним перерендерингам и усложнению логики синхронизации с localStorage; RTK здесь проще и масштабируемее.
- Webpack — мощный, но в современных простых SPA Vite быстрее и легче в конфигурации.
- Tailwind — даёт быстрый прототипинг, но добавляет другой стиль написания UI; я решил придерживаться CSS Modules, чтобы стили оставались декларативными и локальными.

## Методология архитектуры — FSD (Feature-Sliced Design)
- Я организовал проект по принципам FSD: `app`, `entities`, `features`, `shared`, `pages` и т.д. Для меня это удобный способ держать доменную логику и UI отдельными: `entities` содержит модели и UI сущностей (product, cart), `features` — поведение и композицию этих сущностей (например, каталог и фильтры), `shared` — переиспользуемые компоненты и утилиты.
- Почему FSD лично для меня рабочий вариант: при росте приложения мне важно, чтобы новые фичи можно было добавлять минимально влияя на остальной код. FSD облегчает навигацию по коду, упрощает тестирование и даёт понятные границы для рефакторинга.
- Личный опыт: работал с FSD в прошлом проекте и видел выигрыш в поддерживаемости в командах от 3‑5 человек. Это не единственно верный подход, но для SPA, которые планируется расширять, он меня устраивает и я использую его сознательно.

## Краткая структура проекта (важные места)
- `src/app/` — app‑level (провайдеры, глобальные стили, store) — соответствует FSD `app`
  - `store/` — `store.ts`, `hooks.ts`, `types.ts`
  - `providers/` — ThemeProvider, ToastProvider, QueryProvider, ErrorBoundary
  - `styles/` — переменные и темы (light/dark)

- `src/entities/` — сущности (domain)
  - `product/` — api, UI компоненты `ProductCard`
  - `cart/` — `model/cartSlice.ts`, селекторы

- `src/features/` — фичи/поведение (catalog)
  - `ProductList/` — фильтры, сортировка, пагинация

- `src/shared/` — переиспользуемые UI и утилиты
  - `ui/` — Button, Skeleton, ResponsiveImage, Toast, ThemeSwitcher, Cart UI
  - `lib/` — helpers: image, format, localStorage

- `config/` — конфиги сборки (vite/rollup/terser plugins)
- `config/tests/` — конфиг и setup для Vitest

## Как запустить локально
Ниже приведены команды для Windows PowerShell (путь проектной папки — `D:\mycode\shop_test`, команды предполагают, что вы находитесь в корне проекта).

1. Установить зависимости:

```powershell
npm install
```

2. Запустить dev сервер (HMR)

```powershell
npm run dev
```

Откройте http://localhost:5173 если dev-сервер поднялся.

3. Сборка для продакшена:

```powershell
npm run build
```

4. Локальный просмотр собранной версии (preview):

```powershell
npm run preview
```

5. Запуск тестов (Vitest):

```powershell
npm test
```

## Скрипты (из `package.json`)
- `npm run dev` — development server (Vite)
- `npm run build` — production build
- `npm run preview` — preview built app
- `npm test` — запускает Vitest (конфиг в `config/tests/vitest.config.ts`)

## Тесты
Тесты покрывают утилиты и ключевые UI‑компоненты (например, карточку товара, корзину). Тестовая конфигурация использует:
- `config/tests/setupTests.ts` — подключает `@testing-library/jest-dom`.
- `config/tests/test-utils.tsx` — render wrapper для тестов: оборачивает в `Provider` (Redux), `QueryClientProvider` (React Query), `MemoryRouter`, `ThemeProvider` и `ToastProvider`.

## Важные реализации и примечания
- Кэширование: сетевые запросы оборачиваются `react-query` (QueryClient) для кеширования + контроль lifetimes. Также cart кешируется в `localStorage` с TTL (в `src/app/store/store.ts` используется `loadCachedState`/`saveCachedState`).

- Skeleton loaders: приложение использует `Skeleton` компоненты (lazy) и Suspense fallback, в тестах моки упрощены.

- ResponsiveImage: реализована оптимизация srcset/resizing. В тестах присутствует защита от jsdom (stub canvas) — реальная проверка качества изображений и конвертацию в AVIF/WEBP . В коде предусмотрена безопасная проверка поддержки AVIF.

- Toast и Theme: `ToastProvider` вынесен в `src/app/providers/ToastProvider`, `useToast` — в `lib` внутри провайдера. ThemeProvider реализует хранение выбора темы в `localStorage`.
